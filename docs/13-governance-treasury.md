# 13. Управление: трёхпалатный DAO с приоритетом welfare

## 13.1. Почему обычный «1 токен = 1 голос» здесь не работает

Владение токеном не равно компетентности в содержании животных, а в нашем случае **решения DAO напрямую влияют на живые существа**. Значит, нужно разделение: экономические решения — у держателей капитала; этические/ветеринарные — у тех, кто несёт ответственность за благополучие; операционные — у тех, кто исполняет.

```
┌────────────────────────────────────────────────────────────────────┐
│  P1 · Economic Chamber      — 60% веса $BUNNY (staked ≥ 90 дней)   │
│      бюджет, комиссии, цены CLOVER, партнёрства, листинги, вестинг │
├────────────────────────────────────────────────────────────────────┤
│  P2 · Welfare Chamber       — 1 адрес = 1 голос (soulbound)        │
│      состав: 3 ветеринара (внешние), 2 этолога, 3 представителя    │
│      приютов, 5 выборных «Guardian» (уровень ≥ 10), 2 от резиденций │
│      ВЕТО на любое решение P1, если оно снижает WelfareScore        │
├────────────────────────────────────────────────────────────────────┤
│  P3 · Operations Council    — назначается, сменяется               │
│      SOP, персонал, подрядчики, кризисы; отчётность перед P1+P2    │
└────────────────────────────────────────────────────────────────────┘
Порог принятия: P1 — 40% кворум, 50%+ «обычные», 66.6% «экономические изменения»
                P2 — простое большинство, но «welfare-стандарты» — 2/3
                Совместное — для изменения констант 03.9/06.4 требуется 2/3 обеих палат И timelock 180 дней
```

## 13.2. Что нельзя изменить никогда (неизменяемые константы)

Они вынесены в `ImmutableCore` (контракт без апгрейда):

```solidity
// Экономика: нельзя уменьшить долю welfare-фонда
uint16  public constant WELFARE_LEVY_MIN_BPS      = 1000;   // 10%
uint16  public constant DONATION_WELFARE_SHARE_BPS = 1000;  // 10%
// Биология/этика: нельзя «улучшить» продуктивность
uint16  public constant MAX_LITTERS_PER_DOE_YEAR   = 2;
uint16  public constant MAX_LITTERS_LIFETIME       = 4;
uint32  public constant MIN_POST_KINDLING_REST_D   = 120;
uint32  public constant MIN_SALE_AGE_DAYS          = 56;
uint16  public constant MAX_INBREEDING_BPS_ALLOWED = 1250;  // 12.5% hard
// Эмиссия: нельзя включить «награды за игру»
uint256 public constant MAX_DAILY_REWARD_CLOVER    = 900_000e6;
```

Если DAO не может уменьшить долю фонда содержания и увеличить частоту спариваний — главные «дешёвые» способы разворовать ценность исчезают структурно, а не морально.

## 13.3.предложение-процесс

```
1. Draft (soulbound, требует 200 C депозит — burn при отклонении «спам»)
2. Review: P3 оценивает операционную цену; P2 — welfare-риск (обязательное заключение, 7 дней)
3. Snapshot + голосование (14 дней)
4. Timelock: 7 дней (обычные) · 30 дней (экономика) · 90 дней (NFT-механики) · 180 дней (константы)
5. Исполнение через Governor → Timelock → мультиподпись 4/7
6. Post-mortem: через 30 дней — публичный отчёт «что изменилось по метрикам» (04.8)
```

Обязательный элемент: **любаяпредложение об изменении цен/комиссий обязана содержать симуляцию** (наш `simulate.py` — публичный инструмент). Нет расчёта —предложение не проходит техническую проверку. Это резко снижает популизм.

## 13.4. Казна

| Корзина | Доля | Правила |
|---|---|---|
| Welfare Reserve | 20–35% | только по 2 подписям (P2 + внешний ветеринар), 100% отчёт |
| Ops float (стейбл) | 30% | ≥90 дней расходов, алерты 60/45 (04.8) |
| Growth (USDC) | 15% | маркетинг/партнёрства, лимит 10%/квартал |
| Capex (стейбл) | 15% | только с `CapacityProof` |
| BUNNY treasury | 15% | расходы через P1+P2 |
| DIVERSIFIED (ETH/BTC) | 5% | резервный буфер, ребаланс 1/квартал, лимит волатильности |

**Правило «никаких инвестиций в токен проекта»:** казна не покупает собственный BUNNY кроме как через регламентированный buyback-and-burn (03.5), не стейкает в сторонние протоколы с плечом, не даёт займы «команде».

## 13.5. Ответственность резиденции (контрактный уровень)

- С резиденцией заключается **off-chain договор** (SLA) + ончейн-залог `FacilityBond` (20 000 $BUNNY-эквивалент в стейбле).
- Нарушения welfare (подтверждённые P2/инспекцией) → **слашинг залога**: 25% за инцидент категории B, 50% — категории A (травма/смерть по халатности), 100% + расторжение — категории S (систематическое жестоковое обращение).
- Слэшенные средства — только в Welfare Reserve, на реабилитацию животных.
- Смена резиденции — «Portability»: все животные переводимы (чип + медкарта + поведение-профиль), потому что владелец животных — сообщество/фонд, а резиденция — подрядчик. **Технически это главный анти-«заложник» механизм:** проект не может быть уничтожен произволом одного объекта.

## 13.6. Отчётность (обязательная, публичная, на.chain-хеш)

| Отчёт | Период | Содержание |
|---|---|---|
| Welfare Report | месяц | CareScore/WelfareScore популяции, инциденты, эскалации, смерти с причинами |
| Finance Report | месяц | доходы/расходы в USDC, энддаументы, «1 донат = 1 строка сметы» выборочно |
| Vet Report | квартал | результаты независимой инспекции, изменения SOP |
| Treasury Proof | квартал | Merkle-корни балансов, распределение фондов |
| Impact Report | год | животные в приютах, спасённые, стерилизации, гранты НКО |
